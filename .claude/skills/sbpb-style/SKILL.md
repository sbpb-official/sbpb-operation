# SBPB 운영실 취향 가이드

운영진(테니스 동호회 사방팔방)이 휴대폰으로 주로 쓰는 관리 앱. 아래는 지금까지의 요청 · 피드백에서 확인된 취향이다. 새 화면을 만들 때도 이 기준으로 먼저 판단한다.

## 1. 문구

- **명사형 종결**만 사용. 해요체 · 합니다체 금지.
  - 좋음: `페어 6팀 저장` · `참석자 4명 이상 선택 필요` · `기록 없음`
  - 나쁨: `저장했어요` · `선택해 주세요` · `기록이 없습니다`
- **규정집 문체**: 안내 · 규칙 설명은 공식적이고 건조하게. 구어체("덜 붙은", "조금", "항상 먼저") 대신 정확한 명사구.
  - 예: `직전 10회 정기모임 기준 동일 파트너 편성 빈도가 낮은 조합 우선 편성, 레벨 균형 기준에 우선하지 않음`
- **위치 지칭어 금지**: 왼쪽 · 오른쪽 · 위 · 아래 · 하단 대신 섹션 이름으로 지칭 (`모임 설정 › 코트`, `참석자 목록에서`).
- 구분자는 ` · `, 경로는 ` › `, 변경은 ` → `.
- 직관적인 단어: 확인/취소처럼 헷갈리는 버튼 대신 행동을 그대로 (`새 대진으로 복사` / `원본 날짜 수정`).
- 같은 대상은 한 가지 이름으로 통일 (예: "일회성" → "임시 게스트"로 바꾸면 앱 전체에서 바꿈).
- 지역 표기: 서울은 `서울시 ○○구`, 경기는 `경기도 ○○시`.
- **업데이트 기록(NEWS) 문체**: 결론만 공식적으로 짧게. `대상 + 무엇을 + 추가·수정·개선·조정 (목적·범위)`.
  - 바꾸기 전 상태 · 과정 · 감상 쓰지 않음. 숫자 변경만 `0px>16px`처럼 짧게.
  - 약어: MO ver. · PC ver. · TOP. 색 표현은 `컬러`, 묘사어("누런", "칙칙한") 금지.
  - 좋음: `TOP 버튼 노출 방식 개선 (스크롤 위치 따라 페이드 인 · 아웃)` · `대진 통계 박스 간격 조정 (0px>16px)`
  - 나쁨: `TOP 버튼: 갑자기 나타났다 사라짐 → 스크롤에 따라 자연스럽게 흐려짐`

## 2. 시각 디자인

- 딥그린 헤더, 넓은 면은 중립 회색. 순백 · 순흑 금지. 초록(`--court`)은 포인트로만.
- 색은 의미 고정: 같은 의미 = 같은 색 · 같은 모양. 한 색에 두 뜻을 싣지 않음.
  - 주민 우선 = 주황(`--warn`) — 배지 · D-day · 상자 테두리 · 배경까지 한 색으로.
  - 남 = `--male`(파랑 계열), 여 = `--female`(분홍 계열).
  - 경기 종류: 남복 하늘 · 여복 코랄 · 혼복 연초록 · 잡복 회색 (단식은 같은 계열).
  - 바닥: 하드 파랑 · 클레이 주황 · 인조잔디 초록.
  - 토요일 · 일요일은 튀지 않는 파랑 · 빨강(`--sat-soft` / `--sun-soft`).
- 키 컬러가 정해진 상자 안의 요소는 그 키 컬러로 맞춤 (주황 상자 안에 초록 글자 금지).
- 직접 입력한 값은 본문색, 고정 단위(면 · 원 · 시간당)만 회색.

## 3. 간격 · 정렬 (눈이 편한 화면)

- 간격은 4px 단위(4 · 8 · 12 · 16 · 24 · 32).
- 같은 묶음 안(배지↔글자, 아이콘↔글자)은 4–8px로 **일정하게**, 묶음 사이는 16px 이상.
- 정렬보다 **간격 일정**이 우선: 배지 길이가 달라도 뒤 글자와의 간격은 항상 같게. 짧은 배지를 억지로 같은 폭으로 늘리지 않음.
- 가로 · 세로 중심 정렬을 항상 확인 (배지 안 글자, 날짜 박스 안 글자, 줄 단위 세로 가운데).
- 너무 넓지도 좁지도 않게: 버튼과 옆 글자가 붙어 보이거나 멀어 보이면 안 됨.
- 글자 대비 WCAG AA, 본문 줄간격 1.4–1.6, 휴대폰 입력 글자 16px 이상, 누르는 영역 40–44px 이상.
- 긴 문구는 버튼 · 칸 안에서 줄바꿈. 창 밖으로 넘치거나 잘리면 안 됨.
- PC 표: 정보 순서가 자연스럽게(예: 거주 · 직장 · 전화번호 · 상태 · 메모), 메모 같은 부가 칸은 좁게, 잘리는 칸은 넓게.

## 4. 상호작용

- 모달은 **고정 크기 + 내부 스크롤**, 모달 안에 모달을 또 띄우지 않음(큰 입력은 전용 편집 창).
- 드롭다운은 **누른 자리에서 아래로** 펼침. 직접 입력으로 바꾼 뒤에도 다시 목록으로 돌아갈 수 있어야 함.
- 토스트는 화면 가운데.
- 휴대폰 기본 confirm/alert 대신 테마에 맞춘 선택 창(`choiceDialog`), 선택지에 결과 설명을 함께.
- 아코디언은 **제목 줄 전체**를 눌러도 열고 닫힘 + `펼치기/접기` 표시. 열어 둔 상태는 기기에 기억.
- 팝업 · 메뉴는 같은 것을 다시 누르면 닫힘.
- 목록 행은 칸이 아니라 **줄 전체**가 눌림.
- 배치 · 순서 정하기는 끌어다 놓기 + 보조 수단(빈 칸 누르면 목록 선택, 채워진 칸 누르면 빼기).
- 날짜는 캘린더(화살표 크게 · 좌우 스와이프로 월 이동), 연월 · 생년월일은 휠, 시간은 10분 단위 휠.
- 숫자 칸은 숫자만 입력, 단위는 칸 옆 고정 글자. 다시 누르면 전체 선택.
- 정렬 기본값은 가나다순. 묶음이 있으면 묶음 순서 다음 가나다 (예: 게스트 → 미등록).
- 잘못 누를 수 있는 작업은 되돌릴 수 있게 (합치기 되돌리기 등).

## 5. 기능 설계 원칙

- 행사마다 따로 만드는 일회성 로직보다 **표준화된 옵션 조합 + 수정 가능한 프리셋**.
- 자동 생성만 두지 않고 **직접 입력**도 함께 (현장에서 정하는 경우가 많음).
- 흐름은 실제 운영 순서대로: 행사 상세에서 형식 · 팀 · 페어 설정 → 대진 → 끝나면 히스토리.
- 설정값(운영 시간 · 코트 설정)과 규칙(생성 로직)을 섞어 설명하지 않음.
- 지난 기록은 기억이 흐릿하므로 점수 없이 승패 · 결과만 남길 수 있게.
- 개인정보(이름 · 생일 · 전화번호)는 공개 저장소 코드에 넣지 않음. 사용자가 앱의 가져오기로 넣는 파일로 전달.

## 6. 작업 · 보고 방식

- **기획 먼저, 확인 후 코딩**: 요청을 받으면 바로 코드를 고치지 않음. 바뀌는 화면 · 동작을 2–3개 선택지(장단점 · 추천 표시)로 먼저 제시 → 사용자가 고르거나 수정 → 확정안 요약 → 사용자가 "진행"을 확인한 뒤에만 코드 수정 · 배포. 확인 없이 고쳤다 되돌리는 반복은 토큰 낭비이므로 금지.
- 요청 범위를 넘는 변경은 먼저 묻기. 애매하면 결정할 것만 짧게 목록으로.
- "사소한 것도 놓치지 말 것": 모든 UI 변경은 업데이트 기록(NEWS)에 한 줄씩 (규칙은 CLAUDE.md).
- 배포 전 휴대폰 크기(다크 모드 포함)로 화면을 띄워 확인하고, 확인 못 한 부분은 그렇다고 말함.
- 보고는 짧게: 무엇을 바꿨는지 → 어떻게 확인했는지 → 정할 것. 표는 비교할 때만.
